NonEqSimGPU Refactor Plan for a Clean, NHC-Ready Integrator Architecture
Version: Draft 2
Date: 2026-04-22
Status: Approved refactor plan before NHC implementation

======================================================================
0) PRIMARY OBJECTIVE
======================================================================

Refactor the stepping architecture of NonEqSimGPU so that integrator-independent
simulation logic is centralized, integrator-specific logic is isolated behind a
clear protocol, and future deterministic thermostats such as Nose-Hoover Chain
(NHC) can be added without bending the code around Langevin-specific assumptions.

This refactor is the required precursor to a robust NHC implementation.

The goal is not to redesign the physics or rewrite force kernels. The goal is
to cleanly separate:

1. Core simulation state and shared orchestration
2. Integrator-specific algorithms and workspaces
3. Diagnostics, observables, and compatibility wrappers

The resulting architecture must remain allocation-free in steady-state stepping,
preserve GPU specialization, and keep legacy user scripts working during the
migration period.

======================================================================
1) HIGH-LEVEL DESIGN DECISIONS
======================================================================

These decisions are part of the implementation contract.

D1. The new stepping API must be stage-driven, not hardcoded around
    "position / force / velocity" only.
    Reason: that decomposition fits Velocity Verlet, but it is not general
    enough for BAOAB, Brownian midpoint, or Nose-Hoover Chain.

D2. The canonical stepping interface must be:

    step!(st, spec, dt; compute_energy=true)

    where `spec` is the concrete integrator specification.

D3. Legacy `step!(st, dt)` must remain temporarily as a compatibility wrapper.
    It may use a stored default integrator policy during migration, but the
    new architecture must treat explicit `spec` as the real API.

D4. `SimulationState` must become integrator-neutral.
    It must not own Langevin-only or thermostat-specific work buffers.

D5. Integrator workspaces must be owned by the integrator specification,
    not by `SimulationState`.

D6. Diagnostic observables must be part of the architecture early, not an
    afterthought in the writer layer. This is especially important for NHC.

D7. Thermostat-relevant degrees of freedom must be explicit and correct.
    NHC must not infer them implicitly from unrelated code paths.

D8. Integrator naming and semantics must be explicit.
    In the current package, `velocityverlet` / `VV` refers to the
    Grønbech-Jensen/Farago Langevin integrator, not to deterministic MD/NVE
    Velocity Verlet. The refactor must preserve that distinction instead of
    treating "VV" as a generic MD baseline.

======================================================================
2) SCOPE
======================================================================

In scope:
- Stepping architecture in the simulation core
- Integrator protocol definition
- Integrator workspace ownership and lifecycle
- Refactor of existing Langevin `velocityverlet` (GJF/VV) / BAOAB / BAOA / GSM /
  Brownian / EM paths
- Filters and writers where they assume Langevin-specific semantics
- Compatibility wrappers and migration path
- Tests and documentation required to stabilize the refactor

Out of scope:
- Full Nose-Hoover Chain implementation
- Rewriting nonbonded or bonded force kernels
- Changing physical conventions unless required to make API semantics explicit
- Deep redesign of the force model or neighbor-list machinery

======================================================================
3) EXISTING PROBLEMS THAT MUST BE FIXED
======================================================================

P1. `SimulationState` currently embeds thermostat-specific assumptions.
    Examples:
    - hardcoded `vv`
    - globally owned noise buffers
    - global fields that only make sense for some integrators

P2. `build_simulation(...)` initializes Langevin-specific state unconditionally.
    Current concrete symptom:
    - it constructs `gamma_vec`, `noise_scale`, and `VVParams` during build even
      when the target integrator is deterministic or otherwise non-dissipative
    This prevents clean support for deterministic thermostats like NHC.

P3. Shared orchestration logic is duplicated across multiple `step!` methods.
    Examples:
    - neighbor rebuild checks
    - force preparation
    - freeze hooks
    - collision hooks
    - step counter finalization

P4. The filter API assumes stochastic-thermostat knobs such as gamma and
    noise scale are globally meaningful.

P5. Writer output assumes stochastic-only diagnostics such as `Qtot` from `dq`
    are universally meaningful.

P6. The current architecture still reflects one integrator family instead of
    treating integrators as first-class interchangeable algorithms.

P7. The current code and plan terminology can blur "VV" in two different senses:
    - the package's current Langevin GJF `velocityverlet` implementation
    - a deterministic MD/NVE Velocity Verlet integrator concept
    The refactor must make that distinction explicit in API semantics, tests,
    and documentation.

======================================================================
4) TARGET ARCHITECTURE
======================================================================

Split the implementation conceptually into three layers.

Layer A: Simulation core and shared pipeline
- owns core state
- owns stage-independent orchestration
- owns force/collision/freeze lifecycle
- contains no thermostat-specific assumptions

Layer B: Integrator specifications and stage implementations
- each integrator defines:
  - required workspace
  - stage sequence
  - stage handlers
  - optional observables
  - validation rules

Layer C: Compatibility and user-facing wrappers
- preserves old APIs during migration
- routes legacy constructors and `step!(st, dt)` to the new machinery
- emits deprecations only where intended

Suggested file structure:

- src/Simulation.jl
    core state definitions
    build_simulation
    exports and compatibility glue

- src/SimulationPipeline.jl
    shared step orchestration
    stage driver
    common helper functions

- src/IntegratorInterfaces.jl
    abstract protocol
    default methods
    observable interface
    diagnostics hooks

- src/LangevinIntegrators.jl
    VV / BAOAB / BAOA / GSM implementations under the new protocol

- src/BrownianIntegrators.jl
    Brownian midpoint / Euler-Maruyama implementations under the new protocol

- src/Filters.jl
    generic particle-group tools
    integrator-parameter controls dispatched on spec

- src/Writers.jl
    observable collection and output logic

If file splitting is deferred, keep the same files but clearly separate these
sections in code.

======================================================================
5) CORE API SHAPE
======================================================================

The canonical API after refactor must be:

    step!(st::SimulationState{T}, spec::AbstractIntegratorSpec{T}, dt::T;
          compute_energy::Bool=true) where {T}

Legacy compatibility path:

    step!(st::SimulationState{T}, dt::T; compute_energy::Bool=true) where {T}

This legacy method may temporarily route to a default integrator policy, but the
new internal implementation must not depend on hidden mutable global behavior.

Preferred policy during migration:
- explicit `spec` is the new documented path
- `step!(st, dt)` remains supported for one compatibility window

======================================================================
6) DATA MODEL REFACTOR
======================================================================

6.1 SimulationState cleanup

`SimulationState` must contain only integrator-neutral simulation state.

Allowed examples:
- positions
- velocities
- forces
- previous-force buffers if truly universal
- masses
- box / geometry
- neighbor list data
- freeze masks
- collision flags / metadata
- energy / virial accumulators that are universal
- step counter
- last_integrator id if needed for diagnostics only

Disallowed examples:
- Langevin-only work buffers
- OU noise state that is irrelevant to other integrators
- NHC chain variables
- thermostat parameters that are not universal

6.2 Integrator workspace ownership

Each integrator specification must own its own workspace and parameters.

Examples:
- Langevin spec owns random-force buffers and OU state if applicable
- Brownian spec owns its stochastic workspace
- NHC spec will later own chain variables, thermostat masses, and chain scratch

Corollary:
- `build_simulation(...)` must not eagerly materialize `gamma`, `noise_scale`,
  `corr_time`, `VVParams`, or any other integrator-only parameter block as part
  of core-state construction

6.3 Performance requirement

Do not store abstract integrator objects in hot simulation state.

Do not add fields such as:

    active_integrator::Union{Nothing,AbstractIntegratorSpec{T}}

to `SimulationState` if they participate in hot-path dispatch.

Always prefer explicit concrete `spec` passed into `step!`.

6.4 Temporary compatibility bridge

If legacy scripts expect `st.vv` or similar access paths, provide temporary
shim accessors or compatibility wrappers only if absolutely needed.

Keep compatibility logic out of hot stepping paths.

======================================================================
7) INTEGRATOR PROTOCOL
======================================================================

The protocol must be stage-driven.

Do not make the protocol fundamentally depend on these three fixed hooks only:
- position stage
- force stage
- velocity stage

That pattern may be provided as a convenience for simple integrators, but it
must not define the architecture.

7.1 Abstract integrator type

Define:

    abstract type AbstractIntegratorSpec{T} end

7.2 Required protocol functions

Every concrete integrator must support:

    validate_integrator_inputs!(spec, st, dt)::Nothing
    ensure_integrator_workspace!(spec, st)::Nothing
    integrator_id(spec)::UInt8
    integrator_name(spec)::Symbol
    stage_sequence(spec)::Tuple
    execute_integrator_stage!(spec, st, dt, stage_tag; compute_energy)::Nothing
    collect_integrator_observables(spec, st)::NamedTuple

Default implementations may exist where sensible.

7.3 Stage tags

Use explicit stage tags. For operator-split integrators, define consistent
symbols. Examples:

- :B1
- :A1
- :O
- :A2
- :B2

For generic deterministic or thermostat stages, examples may include:

- :thermostat_pre
- :kick1
- :drift
- :force
- :kick2
- :thermostat_post

The exact labels may vary per integrator, but the labels must be explicit,
stable, and useful in debugging output.

7.4 Important architectural rule

`run_integrator_step!` must be able to drive any integrator by iterating over
its stage sequence and calling `execute_integrator_stage!` for each stage.

That is the core abstraction.

7.5 Why this is required

This is necessary because:
- VV is naturally kick-drift-kick
- BAOAB is naturally B-A-O-A-B
- Brownian midpoint has its own staging
- NHC requires thermostat substeps that do not fit a naive
  position-force-velocity protocol

======================================================================
8) SHARED STEP ENGINE
======================================================================

Implement one shared engine:

    run_integrator_step!(st, spec, dt; compute_energy=true)

Target sequence:

1. validate_integrator_inputs!(spec, st, dt)
2. rebuild_needed = plan_neighbor_rebuild!(st, dt)
3. apply_neighbor_rebuild_if_needed!(st, rebuild_needed)
4. prepare_previous_force_buffers!(st)
5. ensure_reference_forces_ready!(st, compute_energy)
6. ensure_integrator_workspace!(spec, st)
7. for each stage_tag in stage_sequence(spec)
       execute_integrator_stage!(spec, st, dt, stage_tag;
                                 compute_energy=compute_energy)
   end
8. finalize_step_accounting!(st, spec, compute_energy)
9. finalize_step_counter!(st, integrator_id(spec))

Important:
- stage ordering must be explicit
- no stage coupling may be hidden in unrelated helpers
- debug tracing must be able to report integrator and stage clearly

======================================================================
9) SHARED PIPELINE HELPERS
======================================================================

Implement the following shared helpers.

9.1 Neighbor and lifecycle helpers

    plan_neighbor_rebuild!(st, dt)::Bool
    apply_neighbor_rebuild_if_needed!(st, rebuild_needed)::Nothing

Purpose:
- decide and apply neighbor rebuild logic
- trigger any post-rebuild hooks that are genuinely integrator-independent

9.2 Force buffer helpers

    prepare_previous_force_buffers!(st)::Nothing
    ensure_reference_forces_ready!(st, compute_energy)::Nothing

Purpose:
- centralize force-buffer preparation
- avoid repeated copy-paste logic in each integrator

9.3 Hook helpers

    apply_post_position_hooks!(st, stage_tag)::Nothing

Purpose:
- run freeze/collision corrections at explicit points after relevant position
  updates
- `stage_tag` must be recorded for diagnostics

Example stage tags:
- :after_drift
- :after_midpoint
- :after_final_position

9.4 Finalization helpers

    finalize_step_accounting!(st, spec, compute_energy)::Nothing
    finalize_step_counter!(st, integrator_id)::Nothing

Purpose:
- universal bookkeeping only
- integrator-specific observables must come from the observable protocol

======================================================================
10) FORCE EVALUATION REFACTOR
======================================================================

Current force setup code is too repetitive.

Introduce reusable force-evaluation routing helpers. Keep existing specialized
kernels if they are performant, but centralize the branching logic.

Implement wrappers such as:

    evaluate_forces_into_f0!(st, compute_energy)::Nothing
    evaluate_forces_into_f!(st, compute_energy)::Nothing

If needed internally, break this down into:

    evaluate_nonbonded_forces!(st, target_slot, compute_energy)::Nothing
    evaluate_bonded_forces!(st, target_slot, compute_energy)::Nothing
    apply_freeze_spring_forces!(st, target_slot, compute_energy)::Nothing
    combine_virial_if_requested!(st, compute_energy)::Nothing

Rules:
- destination buffer must always be explicit in the function name or signature
- do not use ambiguous helper names like `evaluate_forces!(...)`
- preserve 2D/3D specialization and existing optimized kernels

======================================================================
11) DEGREES OF FREEDOM AND THERMOSTAT SEMANTICS
======================================================================

This must be explicit before NHC is implemented.

Add an explicit helper such as:

    thermostatted_dof(st, spec)::Int

This helper must define the actual number of physical degrees of freedom seen by
the thermostat.

It must account for:
- dimensionality
- frozen particles
- constrained coordinates if applicable
- any particles excluded from thermostat action

Do not let NHC or other thermostats infer this indirectly from unrelated data.

Also add, if useful:

    thermostatted_particle_mask(st, spec)

or an equivalent mechanism if thermostat action can be group-specific.

======================================================================
12) OBSERVABLES AND DIAGNOSTICS
======================================================================

Observables must be refactored into a generic interface early.

12.1 Core observable interface

Implement:

    collect_step_observables(st, spec)::NamedTuple

This should combine:
- universal observables from core state
- optional integrator-specific observables from `collect_integrator_observables`

12.2 Universal observables

Examples:
- step
- Epot_total
- Ekin_total
- virial_total
- temperature_estimate if meaningful and universal

12.3 Stochastic integrator observables

Examples:
- dq_total
- dU_total
- Qtot if it is well-defined for that integrator

12.4 NHC-required future observables

The architecture must already be ready to expose:
- extended_hamiltonian
- thermostat_kinetic
- thermostat_potential
- physical_kinetic
- thermostat_temperature_error or equivalent diagnostic
- chain-state summaries if useful

12.5 Debug tracing

Add optional structured stage tracing.

Examples of required content:
- integrator_name
- stage_tag
- step
- whether force evaluation occurred
- whether neighbor rebuild occurred

This should be lightweight and disabled by default.

======================================================================
13) FILTERS REFACTOR
======================================================================

Split filters into two conceptual groups.

13.1 Group A: integrator-agnostic particle/group operations

Examples:
- resolve particle groups
- assign scalar values
- assign arrays
- freeze_particles!
- unfreeze_particles!

These should remain independent of the integrator.

13.2 Group B: integrator-parameter controls

Examples:
- set_temperature!
- set_friction!
- set_corr_time!
- set_noise_scale!
- future thermostat controls

These must dispatch on integrator specification or integrator parameters, not on
internals of `SimulationState`.

Preferred form:

    set_temperature!(spec, value)
    set_friction!(spec, value)

Convenience wrappers may exist:

    set_temperature!(st, spec, dt, value)

but they must route to integrator-owned state, not mutate hardcoded fields in
`SimulationState`.

For future NHC, the architecture must naturally allow:

    set_thermostat_temperature!(spec, T)
    set_thermostat_timescale!(spec, tau)

======================================================================
14) WRITER REFACTOR
======================================================================

Writers must consume generic observables, not assume stochastic-only columns.

Target model:
- writers request `collect_step_observables(st, spec)`
- writers write the subset defined by schema or configuration

Compatibility requirement:
- preserve existing CSV layout for current user workflows by default during
  migration
- add an extensible schema path for future integrators

Recommended policy:
- default legacy schema remains supported for one migration window
- new observable-based writer path is introduced in parallel

======================================================================
15) CONCRETE STAGE EXAMPLES FOR EXISTING INTEGRATORS
======================================================================

These examples are illustrative and should guide implementation.

15.1 Current package `velocityverlet`: Langevin GJF/VV

This is not the same thing as deterministic MD Velocity Verlet.
It belongs to the Langevin-family migration work and must remain associated with
friction/noise parameters and stochastic observables.

Possible high-level stage sequence:

    (:kick1, :drift, :force, :kick2)

15.2 Deterministic MD Velocity Verlet (future or separate compatibility path)

If the package later exposes a true deterministic MD Velocity Verlet integrator,
it should be modeled as a separate spec or clearly separated compatibility name.
It must not silently reuse the current Langevin `VVParams`/`VVSpec` semantics.

Possible high-level stage sequence:

    (:kick1, :drift, :force, :kick2)

15.3 BAOAB
Possible stage sequence:

    (:B1, :A1, :O, :A2, :B2)

15.4 Brownian midpoint
Use an explicit midpoint-oriented stage sequence that matches the actual method.
Do not try to squeeze it into Verlet semantics.

15.5 Future NHC
Possible high-level stage sequence:

    (:thermostat_pre, :kick1, :drift, :force, :kick2, :thermostat_post)

The thermostat stages themselves may internally perform nested chain propagation.
That detail belongs inside the NHC stage implementation, not in the core engine.

======================================================================
16) BACKWARD COMPATIBILITY POLICY
======================================================================

Compatibility is important, but it must not distort the new architecture.

16.1 Keep during migration
- old `build_simulation(...)` keyword patterns where feasible
- old `step!(st, dt)` path
- old writer schema by default if needed
- old convenience paths that users likely rely on

16.2 Deprecate after one release cycle
- legacy gamma / temperature keywords baked into simulation construction
- assumptions that `SimulationState` owns thermostat-specific buffers
- reliance on hidden default integrator behavior in new examples/docs

16.3 Implementation rule
Compatibility logic must live in wrapper layers, not leak into the new shared
pipeline or into hot-path data layout.

That includes legacy `gamma` / `temperature` build keywords: if they remain
accepted during migration, they must be translated into an explicit stochastic
integrator spec outside the integrator-neutral core builder.

======================================================================
17) BUILD PIPELINE REFACTOR
======================================================================

Target construction flow:

1. Build core simulation state only:

       st = build_simulation(...)

   Requirements for this step:
   - allocate only integrator-neutral state
   - do not derive stochastic parameters from `gamma` or `temperature`
   - do not create `VVParams` or any thermostat-specific parameter object
   - do not require dissipative inputs when the eventual integrator does not use
     them

2. Construct integrator specification explicitly:

       spec = velocityverlet(st; gamma=..., temperature=...)
       spec = baoab(st; ...)
       spec = brownian_em(st; ...)
       spec = nhc_velocityverlet(st; thermostat_temperature=..., tau=...)
       spec = nosehooverchain(st; ...)     # future

   Requirements for this step:
   - stochastic spec constructors allocate and validate their own `gamma`,
     `noise_scale`, and correlation-time buffers
   - deterministic spec constructors must not depend on hidden `st.vv` state or
     on dummy friction inputs carried through build
   - compatibility shims may synthesize a default spec here, but not earlier

3. Advance using:

       step!(st, spec, dt; compute_energy=true)

Transitional support:
- legacy `build_simulation(...)` keywords may still be accepted temporarily
- legacy `step!(st, dt)` may internally resolve to a default spec

But the new documentation and examples should move to explicit `spec`.

18) TEST STRATEGY
======================================================================

18.1 Baseline capture before refactor
Before changing behavior, strengthen the current test suite where necessary.

Add:
- small deterministic golden-step tests
- energy/trajectory parity checks where appropriate
- regression cases for neighbor rebuild, freeze, and collision behavior

18.2 Architectural invariants
Add tests that verify:
- neighbor rebuild decisions are unchanged where expected
- freeze hooks run at correct stage points
- collision hooks run at correct stage points
- steady-state stepping remains allocation-free
- force buffers are prepared correctly across stages

18.3 Integrator migration parity
For each migrated integrator family, test:
- same results as before within expected tolerance
- no change in stage order semantics
- correct observables still produced
- current `velocityverlet` parity is checked against the existing Langevin/GJF
  behavior, not against deterministic MD expectations

18.4 Compatibility tests
Test that:
- old `build_simulation + step!(st, dt)` workflows still run
- old user-facing filter calls still route correctly
- old writer outputs still work in compatibility mode
- legacy stochastic build keywords are translated by wrappers without forcing
  deterministic/NHC-ready builds to allocate stochastic state
- any legacy `velocityverlet` compatibility path still resolves to the current
  Langevin semantics unless and until an explicitly separate MD integrator is
  introduced

18.5 Build-contract tests
Add tests that verify:
- `build_simulation(...)` succeeds for deterministic or NHC-targeted workflows
  without requiring meaningful `gamma`
- no unconditional `gamma` / `noise_scale` / `VVParams` construction remains in
  the core build path
- stochastic specs still allocate their required buffers lazily and correctly
- deterministic specs do not read hidden Langevin buffers

18.6 Diagnostics tests
When stage tracing is enabled, verify:
- stage trace is complete and ordered
- stage names are correct
- errors include integrator name and stage tag

18.7 Performance tests
Benchmark after each migration phase.
Reject refactor changes that introduce hot-path dynamic dispatch or allocations.

19) IMPLEMENTATION PHASES
======================================================================

Phase 0: Baseline capture
Tasks:
- strengthen missing regression tests
- record current performance baselines
Exit criteria:
- suite green
- baseline metrics stored

Phase 1: Shared pipeline helpers
Tasks:
- add neighbor rebuild helpers
- add force-buffer preparation helpers
- add finalization helpers
- wire the current Langevin `velocityverlet` path through the new helpers
Exit criteria:
- Langevin `velocityverlet` behavior unchanged
- code duplication reduced

Phase 2: Stage-driven integrator protocol
Tasks:
- introduce `AbstractIntegratorSpec`
- introduce `stage_sequence(spec)`
- introduce `execute_integrator_stage!`
- implement shared `run_integrator_step!`
- route the current Langevin `velocityverlet` path through the new engine
Exit criteria:
- current Langevin `velocityverlet` uses the stage-driven engine successfully
- no hot-path regressions

Phase 3: Migrate Langevin-family integrators
Tasks:
- treat current `VV` / `velocityverlet` explicitly as a Langevin-family member
- migrate BAOAB / BAOA / GSM
- add stage tracing support
- centralize shared force-evaluation routing
Exit criteria:
- all Langevin-family tests pass
- repeated orchestration blocks removed

Phase 4: Migrate Brownian-family integrators
Tasks:
- migrate midpoint / EM
- ensure Brownian semantics fit naturally into stage-driven engine
Exit criteria:
- Brownian tests pass
- architecture remains general, not VV-shaped

Phase 5: Decouple state and build pipeline
Tasks:
- remove thermostat-specific buffers from `SimulationState`
- move workspaces into integrator specs
- refactor `build_simulation(...)` to build core state only
- remove unconditional `gamma` / `noise_scale` / `VVParams` construction from
  the core build path
- move legacy thermostat-keyword translation into explicit spec wrappers or
  compatibility constructors
- add compatibility wrappers
Exit criteria:
- old examples still run through wrappers
- deterministic and NHC-ready builds no longer depend on dissipative keywords
- new explicit construction path documented

Phase 6: Generalize observables, writers, and filters
Tasks:
- implement `collect_step_observables(st, spec)`
- route writers through observable interface
- split generic versus integrator-specific filters
Exit criteria:
- old output paths still supported
- extensible observable path works

Phase 7: Documentation and cleanup
Tasks:
- architecture documentation
- integrator authoring guide
- deprecation notes
- remove retired internal paths approved for deletion
Exit criteria:
- docs complete
- tests green
- compatibility behavior clearly documented

======================================================================
20) IMPLEMENTATION STYLE RULES
======================================================================

R1. Every orchestration-critical function must have a short but precise docstring.

R2. Function names must encode destination buffers or stage semantics clearly.
    Prefer:
        evaluate_forces_into_f0!
        evaluate_forces_into_f!
    over:
        evaluate_forces!

R3. Avoid helper names that hide side effects.

R4. Keep stage transitions explicit in `run_integrator_step!`.

R5. Do not introduce new global mutable state.

R6. Keep concrete types in hot loops.

R7. Do not use abstractly typed fields in performance-critical stepping paths.

R8. Internal code should prefer simple explicit control flow over clever
    metaprogramming unless there is a demonstrated performance need.

======================================================================
21) ACCEPTANCE CRITERIA
======================================================================

The refactor is successful only if all of the following are true:

A1. `SimulationState` is integrator-neutral.
A2. Existing integrators run through one shared stage-driven engine.
A3. Integrator-specific workspaces are no longer globally embedded.
A4. Legacy user workflows still function through compatibility wrappers.
A5. No hot-path allocations are introduced in steady-state stepping.
A6. No meaningful performance regression is introduced.
A7. Writers and filters no longer assume Langevin-only semantics internally.
A8. The architecture is clearly ready for a future NHC implementation.
A9. Stage traceability and debugging are improved compared to current code.
A10. `build_simulation(...)` no longer constructs stochastic friction/noise
     state unless an explicit stochastic compatibility wrapper or spec requests
     it.
A11. The refactor no longer conflates the package's current Langevin
     `velocityverlet` path with a deterministic MD Velocity Verlet integrator.
