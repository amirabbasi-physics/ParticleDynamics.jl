## Overall assessment

### Executive summary

At the level of capabilities you described, this package is already beyond “prototype toy code.” A pure-Julia, CUDA-first engine with GPU-resident cell lists, Verlet lists, CSR-style neighbor structures, stencil lists for unequal sizes, BD/LD/MD integrators, CSVR and Nosé–Hoover-chain thermostats, AOUP support, bonded and nonbonded interactions, and production-loop GPU residency has already crossed the hardest conceptual barrier. The central question is no longer “can this become a real engine?” but “can the internals be reorganized soon enough that future breadth does not collapse performance and maintainability?”

The strongest apparent assets are the right ones: GPU residency is a correct organizing principle; neighbor-list construction on GPU is a serious investment and should be preserved; the integrator menu is already broad enough to support both soft-matter and conventional molecular use cases; and the package is written entirely in Julia, which is a real advantage for long-term hackability, tooling, and specialization. The main risks are architectural rather than scientific: likely CUDA leakage into high-level types and APIs, probable over-centralization of responsibilities in `Simulation.jl`, probable duplication across force/integrator variants, and the absence of an explicit long-term foundation for topology, exclusions, pair coefficients, force fields, restart fidelity, and backend isolation.

My highest-leverage recommendations are these. First, establish a clean public/private boundary before public release. Second, split simulation orchestration from physical state, topology, neighbor-list state, force-field state, and backend workspaces. Third, keep CUDA.jl as the hot-path implementation, but isolate it behind a small internal backend layer rather than allowing `CuArray` assumptions to define the public model. Fourth, redesign pair interactions around concrete potential objects, coefficient tables, neighbor-list policies, and compile-time-specialized kernels. Fifth, build a canonical topology-and-force-field foundation before adding angles, dihedrals, electrostatics, or rigid bodies. Sixth, add a serious validation suite and exact restart design before claiming broad public usability.

The package name change to `ParticleDynamics.jl` is directionally good, but only if the public positioning remains honest. The package should be framed initially as a GPU-first particle-dynamics engine for Brownian, Langevin, and molecular dynamics, currently strongest for coarse-grained, active-matter, and mesoscale particle simulations, with an architecture being prepared for broader molecular-simulation support. It should not yet present itself as a mature general all-atom alternative to established engines.

### Public API evaluation

Without the source, README, and tests, I cannot infer a trustworthy current public API. My default assumption, therefore, is that the repository currently behaves more like a set of internal expert-facing constructors and scripts than a coherent user-facing package. This is normal pre-release and fixable.

For a public package named `ParticleDynamics.jl`, the API should satisfy five constraints at once.

First, simple workflows must be discoverable from high-level constructors and examples. Users should be able to define a system, add interactions, pick an integrator, and run the simulation without touching CUDA.jl internals directly.

Second, advanced users must still be able to control precision, neighbor policies, coefficient tables, backends, filters, launch tuning, writer schedules, and low-level state access.

Third, the public API must not expose raw `CuArray` as a semantic requirement. `CuArray` can remain the current production storage type, but the user model should speak in terms of systems, backends, states, interactions, and writers.

Fourth, the objects that cross into GPU kernels must be concrete, immutable-isbits parameter bundles or compile-time-specialized outer container types. CUDA.jl’s device-kernel model does not permit runtime dispatch in kernels, and Julia performance generally depends on concrete fields and avoiding abstract containers. citeturn9search0turn11search0

Fifth, future CPU support should be selectable cleanly at simulation-construction time, not retrofitted through scattered `Array` versus `CuArray` branches.

My recommended public model is:

- `Backend` objects choose execution target and low-level storage adaptation.
- `System` describes particles, topology, boundary conditions, and static metadata.
- `Simulation` owns a `System`, `DynamicState`, `Integrator`, interaction tuple, backend workspaces, and scheduled outputs.
- `PairInteraction`, `BondInteraction`, and future `AngleInteraction`, `DihedralInteraction`, `Electrostatics` objects are explicit.
- `NeighborList` is explicit, not hidden magic.
- `run!` is the main execution verb.
- `step!` remains public for advanced manual control.
- Exact-restart and writer APIs are separate from stepping.

### Name and scope recommendation

`ParticleDynamics.jl` is a good long-term name. It is broad enough to cover BD, LD, MD, active matter, soft matter, colloids, and eventually more conventional molecular simulation. It is also less misleading than `NonEqSimGPU` for public adoption.

The risk is not the name itself but the implied promise. Public framing should therefore be:

**Recommended positioning:** *A pure-Julia, GPU-first particle-dynamics engine for Brownian, Langevin, active-matter, and molecular simulations, currently strongest for coarse-grained and mesoscale particle systems, with an architecture designed to grow toward broader molecular-simulation support.*

I would avoid presenting it initially as a full general-purpose all-atom molecular engine. That claim becomes credible only after there is a force-field system, angle/dihedral/improper support, exclusions and special-pair scaling, electrostatics with PME, robust restart/I/O, broad validation, and far stronger documentation.

## Core architecture

### Architecture and module-boundary review

The current file split already hints at the eventual architecture, but it is still too “domain-chunked” rather than “responsibility-chunked.” That is normal in research code. It is not yet what I would want for a public, scalable engine.

`Simulation.jl` should not remain the place where package concepts collapse into one another. Its only lasting responsibilities should be: assembling a simulation from validated components, owning the outer run loop, coordinating stage execution, scheduling neighbor-list updates, and scheduling outputs/diagnostics. State definitions, topology definitions, backend-specific buffers, validation, and I/O logic should move out. This refactor can be incremental. First extract pure data types; then extract backend workspaces; then extract output scheduling. After each step, the same integration tests must pass.

`NonBondedForces.jl` should retain the high-level nonbonded interaction API, but not every potential-specific kernel, coefficient-table helper, energy path, virial path, and neighbor-structure branch. Those should be separated into potential definitions, coefficient storage, kernel families, and accumulation modes. This refactor can also be incremental if you start by introducing a single common interface and migrating one potential at a time.

`NeighborLists.jl` should keep list construction, rebuild policy, and neighbor workspaces. It should probably *lose* low-level boundary-condition utilities, general state mutation, and interaction-specific assumptions. Geometry belongs under `Geometry`; exclusions belong under topology or a specialized exclusions module; interaction-specific cutoff semantics belong to interaction policies, not generic list code.

`Filters.jl` should remain only if it becomes a clear particle-selection subsystem. Otherwise it will turn into “miscellaneous conditional behavior.” Selection is important, but the internal concept should probably be `ParticleSelection`, `ParticleMask`, or `ParticleGroup`, with materialized device-side masks or index lists. Thermostats, writers, diagnostics, and active-matter modules can then consume those selections.

`Writers.jl` should keep sink definitions and host-transfer staging. It should lose simulation-loop ownership. In a public engine, the stepper is responsible for scheduling; writers are responsible for serializing and flushing.

The integrator files should be rearranged around method families and operator composition rather than physical-domain labels alone. For example, Brownian, Langevin, and deterministic MD all need shared infrastructure for stages, selections, RNG/noise handling, workspace ownership, and optional thermostat/barostat operators.

### Backend abstraction review

The backend design needs to start from a hard performance truth. CUDA.jl’s kernel model requires compile-time-resolved calls inside kernels, and the host-side `CuArray` abstraction becomes a limited `CuDeviceArray` inside kernels. CUDA.jl also explicitly warns against scalar indexing and recommends disallowing it in development. `Adapt.jl` exists specifically so wrappers and nested structures can preserve shape while swapping storage types. `KernelAbstractions.jl` is a real option for future heterogeneous support, but its own documentation emphasizes that it provides performance portability by emulating GPU semantics, which can mean extra work on CPU and backend-specific profiling/debugging anyway. citeturn9search0turn15search0turn15search2turn13view0turn9search2

That leads to one clear recommendation: **do not try to make the hot path backend-generic too early**.

The right strategy is:

- keep CUDA.jl handwritten kernels for all hot production loops in the near term
- introduce a small internal backend trait layer at the outer API and state-storage boundary
- use `Adapt.jl` patterns for nested container conversion
- add CPU reference implementations first for tests and validation
- add a real CPU production backend later, once interfaces are stable
- defer `KernelAbstractions.jl` experimentation until after the computational interfaces are mature, and only use it where it does not regress performance or clarity

Concretely, I recommend something like:

- `abstract type AbstractBackend end`
- `struct CUDADevice <: AbstractBackend end`
- `struct CPUDevice <: AbstractBackend end`
- `adapt_backend(::CUDADevice, x)` uses `Adapt.adapt`
- `adapt_backend(::CPUDevice, x)` returns host-native storage
- backend-specific kernels live under `Backends/CUDA`
- CPU reference kernels live under `Backends/CPU`
- outer dispatch selects backend implementation **before** control enters a hot loop or kernel

What should *not* happen is this:

- public types with fields literally typed as `CuArray`
- runtime `if backend isa CUDADevice` branches inside inner loops
- `Vector{AbstractInteraction}` or `Vector{AbstractIntegratorStage}` in hot execution
- `KernelAbstractions` introduced just to avoid writing backend adapters, at the expense of currently excellent CUDA control

In other words, make the package *architecturally backend-extensible* now, but keep the implementation *operationally CUDA-optimized* until the rest of the design is clean.

### Simulation-state design

I would strongly avoid the long-term use of a single monolithic `SimulationState` that owns everything from positions to writers to thermostat internal variables to neighbor lists to backend scratch storage. That pattern becomes unmaintainable as soon as you add force fields, exclusions, rigid bodies, PME, or domain decomposition.

The better model is a small set of sharply separated objects:

- `SystemDefinition`: mostly static, physically meaningful data
- `DynamicState`: positions, velocities, forces, box degrees of freedom if any, and step counter
- `Topology`: bonds, angles, dihedrals, impropers, molecule IDs, exclusions, special pairs
- `ForceField`: coefficient tables, type mappings, charge arrays, bonded parameter tables
- `NeighborListState`: list buffers, cell-list buffers, rebuild bookkeeping, displacement trackers
- `IntegratorState`: scheme-specific auxiliary variables, NHC chain variables, CSVR state, active-noise state
- `ObservableState`: optional accumulation/reduction buffers
- `RunContext`: backend object, scratch buffers, output scheduler, validation flags, profiling counters

The public `Simulation` object can own these together. That is a good compromise between user ergonomics and internal separability.

Per-particle data should also be split by mutability. Positions, velocities, forces, orientations, and maybe image/unwrapped counters are dynamic. Masses, diameters, type IDs, particle IDs, and charges are quasi-static. Putting all of that into one large mutable state object is convenient early and expensive later.

The future-proof design should also distinguish:

- canonical host-side definition objects
- backend-adapted device storage
- workspaces/scratch
- build-time metadata that need not survive into hot loops

That separation is what later permits exact restart, analysis-only CPU copies, alternative backends, and domain decomposition.

### Boundary conditions and geometry

Right now support is only periodic boundaries. That is fine. But periodicity should already be represented as a geometry/boundary abstraction, not as ad hoc minimum-image math scattered through force kernels, writers, and initial-condition generators.

I recommend separating:

- `BoxGeometry`: orthorhombic or later triclinic box representation
- `BoundaryCondition`: periodic, mixed periodic/nonperiodic, slab, walls, Lees–Edwards, confinement
- `GeometryOps`: `minimum_image`, `wrap_position!`, `unwrap_delta`, `inside_domain`, `box_matrix`, `inverse_box_matrix`

For performance, these should be concrete types chosen before entering kernels. Do **not** branch on boundary kind inside the hot pair-force loop. Instead, specialize kernels on boundary type or on small static boundary traits. This is the same principle as backend specialization.

Walls and confinement should generally be implemented as explicit interaction objects, not as extra branches inside pair kernels. Mixed periodic/nonperiodic directions can still be supported with a boundary type that carries a static periodicity mask.

### Comparison with established packages

The most relevant lesson from entity["organization","HOOMD-blue","simulation package"] is not “copy the Python API.” It is the separation of simulation operations into composable objects. HOOMD’s MD integrator explicitly organizes forces, methods, constraints, and rigid-body handling, while its pair-force documentation treats neighbor lists and exclusions as first-class concepts. That is a very good architectural north star for a GPU-first engine. ParticleDynamics.jl should imitate that composition model and its clear force/neighborhood boundary, while staying Julia-native in syntax and type structure. citeturn6search2turn6search3turn6search7

The most relevant lesson from entity["organization","LAMMPS","simulation package"] is breadth through style separation and robust neighbor infrastructure. LAMMPS’s documentation shows a huge command/style taxonomy and even multiple neighbor-list request paths. That is exactly the direction a scalable engine eventually needs internally: separate pair, bond, angle, dihedral, and fix-like subsystems built atop a reusable neighbor layer. What ParticleDynamics.jl should *not* imitate is the stringly typed, historically accreted surface language. Keep LAMMPS as an internal architecture lesson, not an API template. citeturn5search1turn5search5turn5search6

The most relevant lesson from entity["organization","GROMACS","simulation package"] is the strict separation between topology and dynamic state. GROMACS documentation distinguishes static atom/topology data, bonded interactions, exclusions, and force-field parameters from dynamic coordinates, velocities, and forces. That is precisely the separation ParticleDynamics.jl needs before all-atom features arrive. What it should avoid copying is the assumption that biomolecular/all-atom conventions should dominate the whole engine. citeturn5search0turn5search4

The most relevant lesson from entity["organization","OpenMM","simulation package"] is architectural layering. The OpenMM manuals expose clean separations among force objects, integrators, platforms, and force-field definition/loading, with explicit custom-force extension paths. That maps unusually well onto Julia’s type system and multiple dispatch. ParticleDynamics.jl should imitate that object-model clarity and backend/platform separation, while using Julia’s compile-time specialization instead of Python/C++ bridging. citeturn12search0turn12search1turn12search3

The most relevant lesson from entity["organization","Molly.jl","Julia package"] is that a modular, extensible, Julia-native simulation API is possible right now in this ecosystem. Molly’s docs and README show a `System`-centric modular model, serious force-field and topology ambitions, PME, constraints, barostats, and broad documentation. ## Performance-critical engine design

### Data layout and performance review

Direct code inspection is blocked, so I cannot state what the package currently stores as `CuArray`s, whether positions are SoA/AoS-like, whether `step!` allocates, or whether scalar indexing protections are enforced. What I *can* say is what must be true for this engine to scale.

The public API must not dictate internal data layout. The internal layout should be picked for coalesced access, low register pressure, and cheap specialization. For dynamic particle kinematics on GPU, two layouts are defensible: a packed vectorized layout per particle, or a structure-of-arrays layout with separate dense component arrays. What is usually *not* acceptable long-term is a deep nesting of small Julia objects per particle in hot device code.

For per-particle scalar metadata, dense flat vectors are the right baseline: masses, diameters, type IDs, charges, molecule IDs, body IDs, and image counters should each live in their own device arrays. Type IDs and topology indices should prefer `Int32` unless there is a proven need for `Int64`, because neighbor and topology structures grow large and index bandwidth matters.

For topological and neighbor structures, CSR-like storage is exactly the right direction. The mere fact that the package already includes CSR-style data structures is a positive sign. On GPU, adjacency-like relationships want flattened index/value arrays plus offset vectors.

Multiple dispatch remains a strength here *if and only if* it resolves before entering hot loops. CUDA.jl is explicit that runtime dispatch is not allowed in kernels, and Julia performance guidance is equally explicit about avoiding abstractly typed fields and poorly typed containers. That means potential objects, coefficient bundles, backend descriptors, and stage operators must be concrete at the moment a run plan is built. A tuple of interactions is good. A `Vector{AbstractInteraction}` is not. An immutable-isbits parameter struct is good. A mutable object with abstract fields is not. citeturn9search0turn11search0

Later file-level inspection should search specifically for these red flags:

- fields typed as `AbstractArray`, `Any`, or abstract supertypes in hot-path structs
- `Vector{Abstract...}` or dictionaries accessed in stepping logic
- `CUDA.@allowscalar` in `src/`
- calls that materialize `Array(...)` or move data host-side inside the production loop
- reductions that implicitly synchronize every step
- stage execution represented as runtime lists of function objects rather than specialized tuples
- noise generation that depends on host RNG APIs for stochastic CUDA updates
- energy/virial computation always enabled, rather than optional and compile-time-selectable

Performance-preserving refactoring should aim for zero-cost abstractions. “Zero cost” here means abstraction only at outer dispatch or compile-time type selection, not at runtime inside kernels. Good examples are backend traits selected outside the kernel, immutable potential objects used as concrete type parameters, and `Val`-style booleans or distinct method families for optional energy/virial paths. Bad examples are abstract interaction lists, generic callback registries on every step, and dynamic branching on backend/potential type deep inside pair loops.

### Neighbor-list and cutoff architecture

The package’s existing neighbor infrastructure is, based on your description, one of its most valuable competitive assets. GPU-resident cell lists, Verlet lists, CSR-style structures, and stencil lists for unequal sizes are already more sophisticated than many research codes ever become. That subsystem should be preserved and generalized, not replaced.

The clean long-term interface is:

- `NeighborSpec`: what an interaction needs
- `NeighborListState`: current built data plus rebuild bookkeeping
- `ensure_neighborlist!`: update or rebuild as needed
- `pair_iteration_mode`: full list versus half list, exclusion policy, search radius model
- `NeighborListKind`: cell/verlet/stencil/etc.

The absolutely crucial design choice is that the neighbor-list builder should be driven by *search policy*, not by the internals of a particular potential. That lets you support:

- global cutoffs
- type-dependent cutoffs
- per-particle search radii for unequal-size particles
- shared neighbor lists among multiple interactions with compatible search requirements
- future ghost/halo patterns for domain decomposition

Skin handling and rebuild criteria should be centralized. A single displacement-tracking policy should decide whether rebuild is needed. That policy should be independent of whether the consuming interaction is LJ, WCA, Yukawa, or tabulated soft repulsion.

Exclusions and bonded special pairs should not be handled by sprinkling ad hoc checks everywhere. Pure exclusions belong in topology/exclusion data. Special 1-4 scaling is a distinct concept and should likely become either a sparse topological interaction list or a specialized nonbonded overlay, not a per-pair dictionary lookup in the main pair loop.

For future multi-GPU domain decomposition, the neighbor interface should assume that “owned” and “ghost” particles may eventually exist. No need to implement that now, but avoid data models that make it impossible.

### Nonbonded-force architecture

`NonBondedForces.jl` is almost certainly where the package will either mature cleanly or stall. The danger is combinatorial duplication across dimension, potential model, neighbor-list kind, backend, energy/virial flags, type logic, all-pairs versus neighbor-list paths, and mixed-size policies.

The scalable design is not “one generic kernel that handles every case.” That usually destroys performance and readability. The scalable design is a small set of interfaces with compile-time-specialized kernels.

I recommend the following internal conceptual layers:

- `AbstractPairPotential`
- `PairParam` types for each potential
- `PairCoefficientTable{P}` mapping type pairs to concrete parameter structs
- `PairInteraction{P,NL,...}` binding potential, coeffs, cutoff policy, and neighbor policy
- `compute_forces!(...)` outer dispatch
- backend-specific kernels specialized on `P`, neighbor-list kind, boundary type, accumulation mode, precision, and optional compile-time flags

For the potential API itself, something close to the following is right:

- `force_energy_virial(potential, r2, param)` returning the force scalar and optional energy/virial contributions
- or separate `pair_force_scalar` and `pair_energy` methods if that leads to simpler specialization

The key is that the *potential type* and *parameter type* are concrete at compile time. That gives you specialization with no runtime dispatch cost.

Type-dependent pair coefficients should be stored in dense, concrete tables indexed by integer type IDs. For modest numbers of particle types, a dense flattened pair-parameter matrix is the obvious design. For many-type cases later, you can revisit compression.

For optional energy and virial paths, I recommend either distinct explicit methods or compile-time flags, not runtime booleans checked inside the inner pair loop. CUDA.jl’s kernel model and Julia’s specialization model both strongly favor compile-time resolution here. citeturn9search0turn11search0

For neighbor-path consumption, interactions should use a shared pair-iteration contract. That avoids duplicating the same loop skeleton for LJ, WCA, Yukawa, tabulated, short-range Coulomb, and active-matter pair laws. You want duplication only where it buys performance, not because the architecture forgot to factor pair traversal from potential logic.

A practical compromise is:

- one kernel family for full neighbor lists with per-particle accumulation
- one optional all-pairs CPU/reference path for correctness tests or very small systems
- one optional half-list path if a future use case really justifies atomics or pair-symmetric accumulation

On GPUs, a full per-particle neighbor list that duplicates pair evaluation often wins because it avoids atomics in force writes. That is a sound default unless and until profiling shows otherwise.

### Bonded topology and future force-field support

Bonded interactions are manageable today only because the scope is still relatively small. As soon as you add angles, dihedrals, impropers, constraints, exclusions, and special-pair rules, the current research-code style will become a liability unless topology and force-field concerns are separated.

I recommend four layers:

- `RawTopology`: canonical connectivity and optional metadata
- `ForceField`: parameter tables, type assignments, charge models, special-pair rules, unit conventions
- `BackendTopologyBuffers`: flattened device-ready connectivity tables
- `TopologyBuilder/Validation`: host-side construction, loading, normalization, and consistency checks

That separation immediately solves several future problems:

- all-atom loaders can stay on the host side
- mesoscale users are not forced to care about residue names or atom records
- exclusions and special-pair scaling become canonical, not scattered
- topology can be validated independently of force-field parameters
- backend adaptation becomes mechanical

A future topology representation should minimally support:

- bonds, angles, dihedrals, impropers
- molecule IDs
- exclusions
- sparse special-pair lists or scaling tables
- optional residue/atom-name metadata side tables
- rigid-body membership
- constraints
- local/ghost ownership fields later

A future force-field representation should support:

- particle/atom types
- masses and charges
- pair coefficients
- bonded parameter tables
- special-pair rules
- unit conventions
- external format loaders as optional host-side builders

Among the big-package design philosophies, I would recommend this blend:

- user-facing composition closer to HOOMD/OpenMM
- topology/force-field separation closer to GROMACS/OpenMM
- internal interaction-style separation closer to LAMMPS
- Julia-native type-driven implementation and ergonomics closer to Molly

I would avoid both extremes: neither a giant style-command system nor a too-magical all-in-one `System` constructor that hides every engine concept.

### Integrator, thermostat, and barostat architecture

Stage-based execution is the right general direction *if* the stages are statically known and the per-stage operators are concrete. That gives you a path to Verlet, BAOAB-like Langevin schemes, Euler–Maruyama, Euler–Heun, NHC, CSVR, AOUP coupling, and later constraints or barostats without degenerating into a tangle of giant `if integrator isa ...` branches.

The most likely current problem is duplication between integrators rather than absence of infrastructure. Brownian, Langevin, and deterministic MD all need some combination of:

- stage scheduler
- force refresh points
- noise generation or consumption
- thermostat updates
- filtered particle subsets
- optional observable hook points
- workspace ownership

That suggests these abstractions:

- `AbstractIntegratorMethod`
- `AbstractThermostat`
- `AbstractBarostat`
- `IntegratorPlan` or `StageSequence`
- `IntegratorState`

The run loop then executes a concrete plan. A good Julia pattern here is a tuple of stage operators, where each operator is a concrete callable struct. That remains explicit, readable, and zero-overhead.

Thermostats should not be tightly fused into unrelated integrator code. CSVR and NHC are not just boolean options; they are operators with state. They should share the same selection/group API, diagnostics interface, and state-storage pattern, even if their math is very different.

AOUP should likewise be treated as a first-class dynamic operator, not a special case hidden in a Langevin file. It is conceptually an active-noise process coupled to particle motion, and it deserves its own state and update operator.

For stochastic schemes, RNG design deserves special attention. CUDA.jl does support GPU-compatible random number generation inside kernels, with explicit caveats around global state, warp-shared behavior, and manual seeding/continuation. That is enough to get started, but exact restart reproducibility will eventually want explicit, owned RNG state or a counter-based RNG strategy, not just reliance on implicit kernel RNG state. citeturn9search0

Barostats, constraints, rigid bodies, and multiple-time-stepping should be planned for at the operator layer now, even if they are not implemented yet. In practice that means:

- keep the box representation separate from ordinary particle arrays
- keep virial/stress interfaces explicit
- do not hard-code “single force refresh point per step” everywhere
- do not assume translational particles are the only dynamic objects forever

## Output, diagnostics, and quality

### Writer, I/O, restart, and trajectory architecture

`Writers.jl` should evolve into a sink architecture with explicit staging boundaries.

The minimum separation is:

- `TrajectoryWriter`: append-only structural snapshots
- `CheckpointWriter`: exact restart state
- `ObservableLogger`: scalar or low-dimensional time series
- `SnapshotBuilder`: pulls only the data needed for a given sink
- `HostTransferPlan`: reusable staging buffers and copy strategy

GPU residency remains mandatory in the production loop. That means host transfers should happen only on scheduled output/diagnostic boundaries, as you requested. Writers must therefore never be “just a convenience call to `Array(state.positions)`” sprinkled into the step loop.

Restart fidelity is a separate concern from trajectory output. A scientifically serious restart file eventually needs:

- positions, velocities, forces if required by scheme
- box state
- topology and force-field identity or hash
- integrator auxiliary state
- thermostat state
- active-noise state
- random-number state
- step counter and output schedule metadata
- backend/precision/version metadata

Trajectory and checkpoint formats do not need to be the same.

If GSD is already present, it may be worth keeping for trajectory interoperability during the GPU-first mesoscale phase, especially given the HOOMD inspiration. But I would not force exact restart onto a trajectory format. Checkpoints should be versioned for the engine itself.

### Observables, logging, diagnostics, and validation

Observables should not be bolted into `step!` or individual integrators in an ad hoc way. They need a scheduler and a low-overhead accumulation model.

I recommend an `Observables` subsystem where each observable declares:

- interval
- what data it needs
- whether it can be done entirely on device
- whether it needs host transfer
- whether it depends on force/virial refresh
- its reduction workspace needs

Examples include:

- kinetic temperature
- potential energy
- virial/stress
- pressure
- MSD
- bond statistics
- AOUP diagnostics
- thermostat energy exchange
- neighbor rebuild counters
- timing/performance counters
- NaN/overflow checks

Common observables should use GPU reductions wherever possible. Optional observables should be truly optional. There should be no always-on energy/virial tax inside the hot loop if the user is not requesting those values.

User-defined observables should be supported, but the API should acknowledge performance reality: a user-defined observable may be host-side and slow, or may need a backend-specific implementation for device execution.

Validation is related but not identical to observables. A `Validation` subsystem should own:

- preflight checks before run
- optional runtime sanity checks
- conservation diagnostics
- thermostat diagnostics
- “unsafe fast mode” toggles if you later want them

### Testing review

I could not inspect the existing tests, so I cannot classify current coverage honestly. My recommendation is therefore about the target test matrix and the order in which to build it.

Before refactoring, create characterization tests around current behavior. They are not the same as ideal tests, but they freeze today’s behavior and reduce accidental regressions while internals move.

During refactoring, use dual-path comparison tests. Every extracted subsystem should continue matching the old implementation on controlled problems until the old path is removed.

After refactoring, the package should have explicit coverage in these categories:

- API smoke tests

### Dependency and packaging review

I could not inspect `Project.toml`, so I cannot identify actual unnecessary dependencies or missing compatibility bounds. That concrete audit remains blocked.

The target dependency policy should nonetheless be clear.

The runtime package should remain lean. Core runtime dependencies should be only those required for the engine to define systems, backends, interactions, integrators, neighbor lists, and writers that are part of the promised public API.

### Code style, naming, conventions, and development rules

ParticleDynamics.jl needs an explicit development convention document before public release. Not because style is intrinsically important, but because performance-sensitive scientific code without conventions decays very quickly.

My proposed rules are:

- public types use clear CamelCase names
- public functions use conventional Julia lower-case names, with `!` for mutation
- internal modules are allowed to be more explicit than pretty
- user-facing constructors are keyword-heavy and validating
- internal low-level constructors are positional and non-exported
- core physics parameter objects should be immutable and concrete
- outer state/workspace objects may be mutable
- no abstractly typed fields in hot-path structs
- no `Vector{Abstract...}` or `Dict` lookups in hot execution paths
- backend-specific code must live under explicit backend modules
- raw `CuArray` should not appear in high-level public APIs
- `CUDA.@allowscalar` is forbidden in `src/` except in clearly documented staging/diagnostic code
- every new user-facing feature requires docs, tests, and at least one example
- every new core kernel requires benchmark coverage
- every new interaction requires two-particle correctness tests and finite-difference checks where applicable
- every new stochastic method requires statistical validation tests
- every new boundary feature requires minimum-image and wrapping tests
- units, if supported at all, must terminate at the API boundary and not leak into the hot loop
- dimension handling should be compile-time-specialized where it matters, but not exploded across too many files
- precision handling must be explicit and tested in at least one single-precision and one higher-precision path

## Final recommendations

### Final prioritized recommendations

The ranking below is by impact on long-term success, not by implementation ease.

**Must fix before public release**

1. **Establish a real public/private API boundary.**  
   Right now the greatest risk is that accidental internal patterns become permanent public commitments.

2. **Split simulation orchestration from physical state, topology, workspaces, and output scheduling.**  
   `Simulation.jl` is the likeliest architecture bottleneck and should stop being a conceptual dumping ground.

3. **Isolate CUDA-specific assumptions behind a thin internal backend layer while keeping CUDA.jl as the hot path.**  
   Do not rewrite hot kernels into a portability layer yet. Use compile-time backend dispatch outside kernels. CUDA.jl, Adapt.jl, and KernelAbstractions.jl together strongly support this staged approach. citeturn15search0turn13view0turn9search2turn9search0

4. **Redesign nonbonded interactions around concrete potential types, concrete pair-parameter tables, and shared traversal interfaces.**  
   This is the highest-leverage scientific-architecture change.

5. **Add a canonical topology/exclusion/special-pair foundation before expanding further into all-atom features.**  
   Without this, future angles/dihedrals/PME work will accumulate technical debt faster than capability.

6. **Build a validation-first test suite, including CPU reference tests and strict GPU-residency checks.**  
   CUDA.jl explicitly warns against scalar indexing and host fallbacks; your CI should enforce that. citeturn15search0

7. **Create exact checkpoint/restart capability distinct from trajectory writing.**  
   Public scientific software needs reproducibility, not just movie output.

8. **Stand up real documentation with Documenter and task-based examples.**  
   Documenter is the standard, supports doctests, and integrates well with CI deployment. citeturn7search0turn7search4

**Should fix soon after public release or during release preparation**

9. **Unify filters/selections, thermostat state, and observable scheduling.**  
   This is the right foundation for barostats, constraints, and subset control.

10. **Clean dependency boundaries aggressively and keep the runtime core lean.**  
    Plotting, benchmarking, and heavy optional I/O should not live in the core runtime package.

**Long-term design improvements**

11. **Add a real CPU production backend only after the current interfaces stabilize.**  
    Start with CPU reference correctness paths.

12. **Evaluate alternative GPU backends only after backend isolation exists and after the hot kernels are measurable and well-factored.**

13. **Add angles, dihedrals, impropers, PME, rigid bodies, and barostats only on top of the new topology/interaction foundation.**

14. **Plan multi-GPU only after single-GPU ownership, ghost-state assumptions, and restart/state models are clean.**

15. **Position the package honestly.**  
    The right near-term niche is not “general all-atom engine.” It is “pure-Julia, GPU-first particle dynamics for BD/LD/MD, especially strong for coarse-grained, active-matter, and mesoscale simulations, growing toward broader molecular support.”

If I had to compress all of this into one sentence, it would be this: **preserve the package’s current CUDA-first performance strengths, but reorganize the internals now around explicit state, topology, interaction, and backend boundaries so that future breadth arrives as extension, not entropy.**
